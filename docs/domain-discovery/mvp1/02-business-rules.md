# هللاتي — Domain Discovery (MVP 1: Open Banking)
## الخطوة 2: Business Rules

نفس طريقة MVP 0: كل قاعدة هنا لازم يصير لها Unit Test.
قواعد MVP 0 (BR-M, U, I, P, B, T, A, G, N) **تبقى كلها سارية**. هنا الجديد فقط، أو التعديل على القديم.

الرموز:
- **[قرار OB-x]** = حسمته أنت في الخطوة 1
- **[مقترح]** = اقترحته أنا، راجعه
- **[يحتاج تحقق]** = يعتمد على سلوك Lean أو البنوك، نتأكد منه في الـ Sandbox قبل الكود
- بدون رمز = من طبيعة المشكلة أو من شروط Lean / SAMA

## 1. الربط والموافقة (Connection) — BR-C

| ID | القاعدة |
|---|---|
| BR-C1 | **[قرار OB-9]** المستخدم يقدر يربط أكثر من بنك. كل ربط = بنك واحد (Entity واحد عند Lean) |
| BR-C2 | **[مقترح]** ما يُربط نفس البنك مرتين وهو نشط. لو انتهت موافقته، يُعاد ربطه بدل ربط جديد |
| BR-C3 | حالات الربط: **قيد الإنشاء** (فتح Link SDK ولسه ما وصل `entity.created`) ← **نشط** ← **منتهي** (انتهت الموافقة أو ألغاها البنك) أو **ملغى** (ألغاه المستخدم). فقط **النشط** تتم مزامنته |
| BR-C4 | **[قرار OB-7]** مدة الموافقة **12 شهر** من تاريخ الربط |
| BR-C5 | **[مقترح]** تذكير قبل انتهاء الموافقة بـ **14 يوم** ثم **3 أيام** |
| BR-C6 | عند انتهاء الموافقة: العمليات المستوردة **تبقى** وتُحسب، المزامنة تتوقف، والمستخدم يُنبَّه **مرة وحدة**. الميزانية تكمل بالتسجيل اليدوي |
| BR-C7 | **[مقترح]** إعادة الربط تكمل على نفس الربط: نستورد من **آخر مزامنة ناجحة** فقط، مو 3 أشهر من جديد |
| BR-C8 | **[مقترح]** إلغاء الربط ما يكتمل إلا بعد ما يأكد Lean إلغاء الموافقة. إذا فشل الطلب، نعرض خطأ والربط يبقى كما هو |
| BR-C9 | **[قرار OB-8]** عند إلغاء الربط يختار المستخدم: **يحتفظ** بالعمليات (تبقى وتُحسب، ومكتوب عليها "من بنك غير مربوط") أو **يحذفها** (تنحذف وتنعاد حسابات الميزانية) |
| BR-C10 | **[مقترح]** حذف الحساب (UC-06): نلغي كل الموافقات ونحذف الـ Customer عند Lean. **بياناتنا تنحذف حتى لو فشل طلب Lean**، ونعيد المحاولة معه في الخلفية |
| BR-C11 | ما نخزن أبدًا بيانات دخول البنك. نخزن فقط معرّفات Lean (`customer_id`, `entity_id`) |
| BR-C12 | مفاتيح Lean (App Token, Client Secret, Webhook Secret) في الـ Backend فقط. التطبيق ياخذ **Token مؤقت** خاص بالمستخدم لفتح Link SDK |
| BR-C13 | **[مقترح]** نطلب أقل صلاحيات ممكنة: **الحسابات، الأرصدة، العمليات** فقط. بدون الهوية، المستفيدين، الأوامر المستديمة |

## 2. المزامنة (Sync) — BR-S

| ID | القاعدة |
|---|---|
| BR-S1 | **[قرار OB-6]** المزامنة تبدأ من: فتح التطبيق، أو الجدولة اليومية، أو سحب المستخدم للتحديث |
| BR-S2 | **[مقترح]** حد أدنى **4 ساعات** بين طلبي تحديث لنفس الربط. فتح التطبيق داخل هذي المدة يقرأ من قاعدتنا فقط |
| BR-S3 | **[مقترح]** التحديث اليومي الساعة **6 صباحًا** بتوقيت الرياض، قبل يوم المستخدم |
| BR-S4 | الاستيراد يبدأ فقط بعد Webhook `entity.data.refresh.updated` بحالة `FINISHED`. وصول `entity.created` ما يطلب بيانات (شرط Lean) |
| BR-S5 | **الاستيراد لا يكرر:** كل عملية بنكية معرّفة بمعرّفها عند المزود. استيرادها مرة ثانية **يحدّثها** ولا ينشئ نسخة |
| BR-S6 | **[مقترح]** نافذة الجلب: من آخر مزامنة ناجحة **ناقص 7 أيام**، عشان نلقط العمليات المعلّقة اللي تغيّرت |
| BR-S7 | قاعدتنا هي مصدر الحقيقة للتطبيق. Lean يحتفظ بالبيانات 30 يوم فقط |
| BR-S8 | كل Webhook يُتحقق من توقيعه بالـ Webhook Secret، والمرفوض ما يُعالج. ومعالجة نفس الحدث مرتين = مرة وحدة |
| BR-S9 | فشل المزامنة ما يمسح شيء: البيانات الأخيرة تبقى، ويظهر "آخر تحديث قبل X" |

## 3. العملية المستوردة (Imported Transaction) — BR-X

| ID | القاعدة |
|---|---|
| BR-X1 | `DEBIT` = صرف يدخل الميزانية. `CREDIT` = مبلغ داخل، يتبع قواعد BR-F |
| BR-X2 | تاريخ العملية = **التاريخ فقط** من `booking_date_time` (البنك يرسله بدون وقت، نتيجة V5)، وهو اللي يحدد فترتها |
| BR-X3 | **[مقترح]** العمليات بغير الريال تُخزن لكن **ما تدخل الميزانية** (BR-M1)، مع ملاحظة للمستخدم |
| BR-X4 | حقول البنك **للقراءة فقط**: المبلغ، التاريخ، التاجر، الحساب. المستخدم يغيّر فقط: **الفئة، الملاحظة، الاستبعاد** |
| BR-X5 | العملية البنكية **ما تنحذف**، تُستبعد. الحذف يرجّعها مع التحديث الجاي |
| BR-X6 | **[قرار OB-2]** العملية المعلّقة تُحسب **فورًا**. إذا اكتملت بمبلغ مختلف، أو أُلغيت واختفت، تنعاد حسابات الميزانية |
| BR-X7 | اختيارات المستخدم (الفئة، الملاحظة، الاستبعاد) **تبقى** حتى لو حدّث البنك العملية |
| BR-X8 | **[نتيجة V1]** المعرّفات ثابتة بين التحديثات، وحتى العملية المكتملة ممكن يتغير فيها حقل. فالاستيراد **يحدّث بالمعرّف** دائمًا (BR-S5) |
| BR-X9 | **[مقترح، احتياط V1]** إذا **اختفت** عملية معلّقة من جلب يغطي تاريخها، تُعتبر ملغاة وتنحذف من الميزانية |
| BR-X10 | **[مقترح]** الحسابات اللي **يدخل صرفها الميزانية:** الجاري، البطاقة الائتمانية، Charge Card، مسبقة الدفع، المحفظة الإلكترونية. **الادخار** يُعرض رصيده فقط. وأي حساب بغير الريال يُستبعد (BR-X3). والمستخدم يقدر يغيّر هذا لكل حساب |
| BR-X11 | **[مقترح]** الرسوم المنفصلة (`charge_amount` لما `charge_included = false`) تُضاف لمبلغ العملية في الميزانية |
| BR-X12 | **[قرار OB-12]** **سحب الصراف (ATM)** يُحسب صرفًا ويُصنّف "أخرى" باسم "سحب نقدي"، والمستخدم يقدر يغيّر فئته. السبب: أغلب المستخدمين ما يسجلون مصروفات الكاش بعد السحب، فإذا ما حسبناه تضيع الفلوس من الميزانية |
| BR-X13 | **[قرار OB-14]** إدخال حساب في الميزانية أو إخراجه **يعيد تصنيف عملياته الموجودة**، مو الجاية فقط. عشان كذا نحفظ مع كل عملية نوعها الفرعي **وحسابك اللي كان الطرف الثاني** (مو الـ IBAN) |

## 4. السجل عند أول ربط (History) — BR-H

| ID | القاعدة |
|---|---|
| BR-H1 | **[قرار OB-5]** أول ربط يستورد **3 أشهر** |
| BR-H2 | عمليات ما قبل الفترة الحالية تُخزن وتُستخدم للـ Insights، وما تدخل ميزانية الفترة الحالية |
| BR-H3 | **[قرار OB-5]** الاستيراد الأول **ما يرسل تنبيهات لكل عملية**. بعد ما يخلص، نقيّم كل فئة **مرة وحدة** ونرسل أعلى عتبة فقط (BR-A3). هذا يمنع سيل التنبيهات |
| BR-H4 | **[مقترح، لاحقًا]** بعد أول ربط، نقترح حدود للفئات من متوسط صرف 3 أشهر |

## 5. التصنيف التلقائي (Categorization) — BR-K

| ID | القاعدة |
|---|---|
| BR-K1 | ترتيب التصنيف: **قاعدة المستخدم للتاجر** ← تصنيف Lean أو رمز النشاط (MCC) ← **"أخرى"** |
| BR-K2 | لما يغيّر المستخدم تصنيف عملية ويختار "دائمًا"، تصير **قاعدة للتاجر**: تنطبق على الاستيرادات الجاية، و **[مقترح]** نعرض تطبيقها على عمليات نفس التاجر في الفترة الحالية |
| BR-K3 | **[مقترح]** التاجر يُطابق باسم **منظّف**: أحرف صغيرة، بدون مسافات زائدة، بدون أرقام الفروع. مثال: "STC PAY 1234" ← "stc pay" |
| BR-K4 | **[مقترح]** تصنيفات Lean الـ 14 (نتيجة V4) تُحوَّل لفئة من فئات **المستخدم** بجدول كلمات (مثل `category_visual`). لو ما فيه فئة مطابقة، أو **درجة ثقة Lean أقل من 0.5** ← "أخرى" |
| BR-K5 | فئة **"الادخار"** ما تُعطى تلقائيًا من تصنيف المزود. **الاستثناء [قرار OB-13]:** التحويل لحساب ادخار المستخدم (BR-R7) |
| BR-K6 | **[مقترح]** العملية المصنفة تلقائيًا تحمل علامة "تلقائي" حتى يراجعها المستخدم أو يغيّرها |

## 6. التكرار: يدوي مقابل بنكي (Duplicates) — BR-D

| ID | القاعدة |
|---|---|
| BR-D1 | **[مقترح]** "يشبه" = مصروف يدوي غير مدموج + عملية بنكية `DEBIT` لنفس المستخدم، **نفس المبلغ بالضبط**، والفرق بين التاريخين **3 أيام أو أقل** |
| BR-D2 | **[مقترح]** اسم التاجر **مو شرط** (اليدوي غالبًا فاضي أو مكتوب بشكل مختلف)، لكن تشابهه يرفع ترتيب الاقتراح |
| BR-D3 | **[قرار OB-1]** ما فيه دمج تلقائي. النظام يقترح والمستخدم يأكد |
| BR-D4 | **[قرار OB-10]** وقت انتظار القرار، تُحسب **العملية البنكية فقط**، والمصروف اليدوي يُعلَّم "مكرر محتمل" وما يُحسب. السبب: أغلب التشابهات تكرار فعلي، وحسابها مرتين يعطي "تقدر تصرف اليوم" أقل من الحقيقة |
| BR-D5 | **تأكيد الدمج:** تبقى العملية البنكية، وتنتقل لها فئة وملاحظة المستخدم من اليدوي، ويُحذف اليدوي |
| BR-D6 | **رفض الدمج:** الاثنين يُحسبان، وما نقترح نفس الزوج مرة ثانية |
| BR-D7 | مصروف يدوي واحد يطابق عملية بنكية واحدة فقط. لو فيه أكثر من مرشح، الأقرب تاريخًا |

## 7. التحويلات وسداد البطاقة (Transfers) — BR-R

| ID | القاعدة |
|---|---|
| BR-R1 | **[نتيجة V2]** **تحويل بين حساباتي** = عملية **IBAN الطرف الآخر** فيها (`creditor_account` / `debtor_account`) يطابق IBAN حساب مربوط **آخر** لنفس المستخدم. وإذا ما فيه IBAN: `DEBIT` من حساب و `CREDIT` في حساب آخر له، بنفس المبلغ، خلال **يومين** |
| BR-R2 | **[نتيجة V2]** Lean ما عنده نوع خاص لسداد البطاقة. **سداد البطاقة = تحويل داخلي** (BR-R1) لأن البطاقة نفسها حساب مربوط. مشتريات البطاقة تُحسب من حساب البطاقة، والسداد ما يُحسب، فما يتكرر الصرف |
| BR-R3 | **[قرار OB-3]** المكتشف كتحويل يُعلَّم ويُسأل المستخدم **كل مرة**: "تحويل" (يُستبعد) أو "صرف" (يُحسب) |
| BR-R4 | **[قرار OB-10]** وقت انتظار الجواب، التحويل المحتمل **ما يُحسب** صرفًا. نفس منطق BR-D4: الغالب أنه تحويل فعلًا |
| BR-R5 | التحويل لشخص آخر (حساب مو مربوط عندنا) = **صرف عادي** ويُصنّف (مثل الإيجار) |
| BR-R7 | **[قرار OB-13]** تحويل من حساب يدخل الميزانية **إلى حساب ادخار** المستخدم = **ادخار**: يُحسب في فئة "الادخار" بدون سؤال. ومبلغ داخل **من** حساب الادخار = رجوع عن الادخار، ينقص الفئة (وما تنزل تحت صفر، BR-F4). قاعدة تاجر من المستخدم تغلب |
| BR-R6 | **[مقترح، لاحقًا]** إذا أجاب المستخدم نفس الجواب لنفس النمط مرتين، نعرض عليه "تذكّر هذا" |

## 8. المبالغ الداخلة (Incoming) — BR-F

| ID | القاعدة |
|---|---|
| BR-F1 | `CREDIT` ما يُحسب صرفًا أبدًا |
| BR-F2 | **[قرار OB-4]** **الاسترجاع** (من تاجر سبق الصرف عنده) **ينقص** مصروف فئة العملية الأصلية، في الفترة اللي وصل فيها الاسترجاع |
| BR-F3 | **[نتيجة V3]** الاسترجاع = `CREDIT` نوعه الفرعي `REFUND` أو `REVERSAL`. **[مقترح]** وإذا ما فيه نوع: `CREDIT` من نفس التاجر المنظّف (BR-K3) لعملية `DEBIT` خلال **60 يوم** سابقة |
| BR-F4 | **[مقترح]** مصروف الفئة ما ينزل تحت الصفر بسبب استرجاع (مثلًا شراء في فترة سابقة واسترجاع في هذي) |
| BR-F5 | **[قرار OB-4]** **الراتب** = اقتراح فقط، ما يتغير الدخل تلقائيًا |
| BR-F6 | **[مقترح]** "يشبه الراتب" = `CREDIT` **≥ 50% من الدخل المسجل**، من نفس المصدر، تكرر في **شهرين متتاليين** بفرق 3 أيام أو أقل في اليوم. حينها نقترح تحديث الدخل أو يوم الراتب |
| BR-F7 | باقي المبالغ الداخلة (تحويل وارد من شخص) تظهر في القائمة وما تأثر على الميزانية |

## 9. تعديلات على قواعد MVP 0

| ID | القاعدة القديمة | التعديل |
|---|---|---|
| BR-T3 | التاريخ ما يكون في المستقبل | ينطبق على اليدوي فقط. تاريخ البنك يُقبل كما هو |
| BR-T5 | تعديل أو حذف مصروف يعيد الحساب | أيضًا: تحديث البنك لعملية، استبعادها، دمجها، أو استرجاع |
| BR-A5 | التنبيهات للفترة الحالية فقط | **يُضاف:** والاستيراد الأول يقيّم مرة وحدة (BR-H3) |
| BR-N7 | تقدر تصرف اليوم | **[قرار OB-11] بدون تغيير:** يعتمد على **الصرف** (بنكي + يدوي)، مو **رصيد الحساب**. الرصيد يُعرض منفصلًا. السبب: الرصيد فيه فلوس مو مخصصة للصرف (ادخار، التزامات) |
| BR-U3 | حذف الحساب يحذف بياناته | **يُضاف:** وروابطه عند Lean (BR-C10) |
