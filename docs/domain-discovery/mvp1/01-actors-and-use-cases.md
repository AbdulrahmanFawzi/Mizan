# هللاتي — Domain Discovery (MVP 1: Open Banking)
## الخطوة 1: Actors و Use Cases

---

## الهدف

المستخدم يربط حسابه البنكي مرة وحدة، والمصروفات تدخل الميزانية **تلقائيًا** بدل ما يسجلها بيده.
كل ما بُني في MVP 0 (الميزانية، الأهداف، التنبيهات، "تقدر تصرف اليوم") يبقى كما هو، والجديد هو **مصدر** العمليات.

---

## كيف يشتغل Lean (حقائق من التوثيق تبني عليها الـ Use Cases)

```
1. ننشئ للمستخدم "Customer" عند Lean            POST /customers
2. الـ Backend يطلب Token خاص بهذا الـ Customer     ثم يعطيه للتطبيق
3. التطبيق يفتح Link SDK                            يختار البنك ويوافق على الموافقة في تطبيق البنك
4. Lean يرسل Webhook: entity.created               "تم الربط" (Entity = ربط واحد مع بنك واحد)
5. Lean يجلب البيانات من البنك ويخزنها عنده
6. Lean يرسل Webhook: entity.data.refresh.updated  بحالة FINISHED = البيانات جاهزة
7. نطلب الحسابات والأرصدة والعمليات               GET accounts / balances / transactions
```

| الحقيقة | أثرها علينا |
|---|---|
| Lean **ما يحدّث البيانات تلقائيًا** إلا عند معالجة الأخطاء | **نحن** اللي نطلب التحديث (`POST /data/v2/refreshes`)، ولازم نقرر متى. التحديث اليدوي "قد يصير مدفوعًا مستقبلًا" |
| Lean يحتفظ بالبيانات **30 يوم** فقط | لازم نخزن العمليات عندنا، ما نعتمد على مخزنهم |
| الموافقة لها تاريخ بداية ونهاية (`access_from` / `access_to`) | الموافقة تنتهي، والمستخدم يحتاج **إعادة ربط** |
| انتهاء أو إلغاء الموافقة يرجع `CONSENT_EXPIRED` ويوصل Webhook `entity.updated` | لازم نكتشف هذا ونطلب من المستخدم إعادة الربط |
| SAMA تلزم إتاحة **إلغاء الموافقة** للمستخدم | لازم زر "إلغاء الربط" داخل التطبيق |
| كل عملية فيها: `DEBIT` أو `CREDIT`، الحالة (pending / booked)، هل قابلة للتغيير (`MUTABLE`)، اسم التاجر، رمز نشاطه (MCC)، وتصنيف مقترح من Lean | نقدر نصنف تلقائيًا، ونتعامل مع العمليات المعلّقة اللي تتغير |
| Webhook `bank.availability.updated` | البنك ممكن يتوقف مؤقتًا، ونعرض هذا للمستخدم |

## Actors

| Actor | من هو | جديد؟ |
|---|---|---|
| **المستخدم (User)** | الشخص المسجل | لا |
| **الوقت (Time / Scheduler)** | يطلب تحديث البيانات بشكل دوري | دوره جديد |
| **مزود Open Banking (Lean)** | نظام خارجي يكلمنا عبر **Webhooks** | ✅ جديد |

> **ملاحظة تصميمية:** البنك نفسه **مو** Actor عندنا. نحن ما نكلم البنك أبدًا، نكلم Lean فقط. وLean نفسه يختفي خلف `IBankingTransactionProvider`، فلو غيرناه لـ Tarabut ما يتغير شيء في الـ Domain.

## Use Cases

### 7. ربط البنك

| ID | Actor | Use Case | ملاحظة |
|---|---|---|---|
| UC-70 | المستخدم | يربط حسابه البنكي | يشوف شاشة الموافقة (وش البيانات، لمين، لين متى) ثم Link SDK |
| UC-71 | Lean | يبلّغنا إن الربط تم | `entity.created`: نسجل الربط، **ما** نطلب البيانات هنا |
| UC-72 | المستخدم | يعرض البنوك والحسابات المربوطة | أكثر من بنك مسموح (OB-9)، مع آخر تحديث وحالة الموافقة وتاريخ انتهائها |
| UC-73 | المستخدم | يعيد ربط بنك انتهت موافقته | الموافقة 12 شهر (OB-7)، ونذكّره قبل انتهائها |
| UC-74 | المستخدم | يلغي ربط بنك (يلغي الموافقة) | **إلزامي من SAMA**. المستخدم يختار: يحتفظ بالعمليات المستوردة أو يحذفها (OB-8) |
| UC-75 | Lean | يبلّغنا إن الموافقة انتهت أو أُلغيت من جهة البنك | `entity.updated` نحدث الحالة وننبه المستخدم |
| UC-76 | Lean | يبلّغنا إن بنك صار متوقف أو رجع | `bank.availability.updated` |

## القرارات (2026-10-25)

قرارات MVP 0 هي D1–D5. قرارات Open Banking مرقمة **OB-1 إلى OB-9** حتى ما تتداخل معها.

| # | السؤال | القرار | السبب |
|---|---|---|---|
| OB-1 | تكرار المصروف اليدوي مع البنكي | **النظام يقترح الدمج، والمستخدم يأكد** | دمج خاطئ لعمليتين حقيقيتين أسوأ من ضغطة زيادة |
| OB-2 | العمليات المعلّقة | **تُحسب في الميزانية فورًا** وتتحدث إذا تغيرت | "تقدر تصرف اليوم" لازم يكون دقيق بعد الشراء مباشرة |
| OB-3 | التحويل بين حساباتي وسداد البطاقة | **النظام يعلّمها ويسأل المستخدم** كل مرة | قرار المستخدم: الدقة أهم من تقليل الضغطات |
| OB-4 | المبالغ الداخلة | **الاسترجاع ينقص مصروف فئته، والراتب اقتراح فقط** | لا نغيّر دخل المستخدم بدون علمه |
| OB-5 | السجل عند أول ربط | **3 أشهر**: الفترة الحالية للميزانية، والباقي للـ Insights، بدون تنبيهات | توازن بين فائدة الـ Insights وثقل الاستيراد |
| OB-6 | التحديث | **عند فتح التطبيق + مرة يوميًا**، مع حد أدنى بين الطلبات لكل بنك | بيانات حديثة، وتنبيهات تشتغل حتى لو ما فتح التطبيق، مع ضبط التكلفة |
| OB-7 | مدة الموافقة | **12 شهر** مع تذكير قبل الانتهاء | إعادة ربط مرة بالسنة |
| OB-8 | إلغاء الربط | **المستخدم يختار:** يحتفظ بالعمليات أو يحذفها | يحترم الخصوصية (PDPL) ولا يكسر ميزانيته رغمًا عنه |
| OB-9 | عدد البنوك | **أكثر من بنك** من البداية | أغلب الناس عندهم أكثر من بنك |
| OB-10 | وقت انتظار قرار التكرار أو التحويل | **تُحسب البنكية فقط، والتحويل المحتمل ما يُحسب صرفًا** | أغلب التشابهات حقيقية، والحساب المزدوج يظلم "تقدر تصرف اليوم" |
| OB-11 | أساس "تقدر تصرف اليوم" | **الصرف مقابل الخطة** (بدون تغيير)، والرصيد يُعرض منفصلًا | الرصيد فيه فلوس مو مخصصة للصرف |
| OB-12 | سحب الصراف (ATM) | **يُحسب صرفًا** تحت "أخرى" باسم "سحب نقدي" | أغلب الناس ما يسجلون مصروفات الكاش بعد السحب |
| OB-13 | التحويل لحساب الادخار | **ادخار تلقائي** في فئة "الادخار" بدون سؤال، والسحب من الادخار ينقصها | (2026-10-26، بعد مراجعتك) التحويل للادخار هو الادخار نفسه، وفئة "الادخار" تقيسه (D4) |
| OB-14 | عملية من حساب خارج الميزانية | **الشاشة توضح السبب** وتعطي زر "أدخل هذا الحساب في ميزانيتي"، والإدخال يعيد حساب عملياته الموجودة | (2026-10-26) كانت الشاشة تخليك تغيّر الفئة بدون ما تقول إنها ما تنحسب |
