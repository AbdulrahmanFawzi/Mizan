# ميزان — Domain Discovery
## الخطوة 4: Aggregates و Domain Events (نطاق MVP 0)

---

## وش هو الـ Aggregate؟

مجموعة Entities و Value Objects تتعامل معها **كوحدة واحدة** لما تعدّل البيانات. لها **Aggregate Root** واحد هو الباب الوحيد للدخول: ما تعدّل شيء داخلها إلا من خلاله.

**ليش؟** عشان القواعد اللي تربط أكثر من شيء تنحمى في مكان واحد. مثال: "كل عتبة تنبيه تنرسل مرة وحدة لكل فئة" (BR-A2) — لو أي كود يقدر يعدّل `HighestThresholdSent` مباشرة، القاعدة بتنكسر يومًا ما.

**ثلاث قواعد لتصميم الـ Aggregates:**
1. **صغيرة قدر الإمكان.** الـ Aggregate الكبير يعني تعارضات أكثر وتحميل بيانات أكثر.
2. **تشير لبعض بالـ Id فقط**، مو بالكائن نفسه. المصروف يحمل `CategoryId`، مو `Category`.
3. **عملية واحدة تعدّل Aggregate واحد.** إذا لازم يتأثر Aggregate ثاني، نستخدم **Domain Event**.

## الـ Aggregates

| Aggregate Root | يحتوي | الـ Invariants (القواعد اللي يضمنها بنفسه) |
|---|---|---|
| **User** | — | البيانات صالحة (بفضل الـ Value Objects)، الدخل > 0 |
| **Category** | — | الفئات النظامية (Other و Savings) ما تنحذف ولا يتغير نوعها (BR-B3) |
| **Budget** | BudgetAllocation | حد واحد لكل فئة، الحدود ≥ 0، كل عتبة تنرسل مرة وحدة (BR-A2)، أعلى عتبة فقط (BR-A3)، ما فيه عتبات لفئة Savings (BR-A4) |
| **Transaction** | — | المبلغ > 0، الفئة إلزامية، التاريخ مو في المستقبل |
| **Goal** | — | المستهدف > 0، التاريخ في المستقبل عند الإنشاء، حساب الادخار الشهري المطلوب (BR-G4، BR-G5) |
| **Notification** | — | يتعلّم كمقروء مرة وحدة |

### قواعد ما يقدر Aggregate واحد يضمنها لحاله

بعض القواعد تحتاج تشوف **أكثر من نسخة** من الـ Aggregate، وهذي ما يقدر يحميها الـ Aggregate نفسه:

| القاعدة | من يضمنها |
|---|---|
| البريد فريد (BR-U1) | فحص في الـ Application + **Unique Constraint** في قاعدة البيانات |
| اسم الفئة فريد لكل مستخدم (BR-B1) | نفس الشيء |
| ميزانية واحدة لكل فترة (BR-P5) | نفس الشيء |
| الفئة تخص نفس المستخدم (BR-T2) | فحص في الـ Application قبل إنشاء المصروف |
| المصروف المرتبط بهدف لازم يكون في فئة Savings | فحص في الـ Application |

**الدرس:** قاعدة البيانات خط الدفاع الأخير، لأن طلبين في نفس اللحظة ممكن يعدّون فحص الـ Application مع بعض.

## Domain Events

**Domain Event:** شيء **صار** في الـ Domain ويهم أجزاء ثانية. يُكتب دائمًا بصيغة الماضي.

بدل ما `RecordExpense` يعرف كيف يرسل تنبيه ويعدّل الميزانية وينشئ إشعار، هو يقول بس "**صار مصروف**"، واللي يهمه الموضوع يسمع ويتصرف. كذا كل جزء مسؤول عن شيء واحد.

| Event | يصير لما | من يسمعه ووش يسوي |
|---|---|---|
| **UserRegistered** | مستخدم جديد سجّل | ينشئ فئتي "أخرى" و"الادخار" + أول ميزانية |
| **MonthlyIncomeChanged** | المستخدم عدّل دخله | يحدّث PlannedIncome في ميزانية الفترة الحالية (BR-I2) |
| **TransactionRecorded** | مصروف جديد | يقيّم عتبات فئته في ميزانية فترته (BR-A1–A5) |
| **TransactionUpdated** | مصروف تعدّل | نفس اللي فوق، للفئة/الفترة القديمة والجديدة (BR-T5) |
| **TransactionDeleted** | مصروف انحذف | يعيد التقييم (بدون إعادة إرسال تنبيه سبق — BR-A2) |
| **BudgetThresholdReached** | الميزانية قررت إن عتبة انقطعت | ينشئ Notification |
| **CategoryDeleted** | فئة انحذفت | ينقل مصروفاتها لفئة "أخرى" (BR-B4) ويحذف حدودها من الميزانيات |
| **GoalCompleted** | مصروف ادخار وصّل الهدف لمبلغه | ينشئ Notification تهنئة |

### مثال كامل: تسجيل 50 ريال بنزين

```
المستخدم ── RecordExpense(50, البنزين, اليوم)
              │
              ▼
        Transaction (Aggregate) ── يتحقق: المبلغ > 0، التاريخ مو مستقبل
              │
              ▼  يُحفظ ويُطلق
        TransactionRecorded
              │
              ▼  Handler
        يحسب مصروف فئة البنزين في الفترة = 450 من 500 (90%)
              │
              ▼
        Budget.EvaluateThresholds(البنزين, 450)
              │   ← هنا الـ Aggregate يطبق BR-A2 و BR-A3 و BR-A4
              │     ويسجل 90 كأعلى عتبة انرسلت
              ▼  يُطلق
        BudgetThresholdReached(البنزين, 90%)
              │
              ▼  Handler
        Notification: "⚠️ استخدمت 90% من ميزانية البنزين"
```

## خريطة العلاقات

```
User ─┬─< Category
      ├─< Budget ──< BudgetAllocation >── Category (بالـ Id)
      ├─< Transaction >── Category (بالـ Id)
      │        └──── Goal (بالـ Id، اختياري)
      ├─< Goal
      └─< Notification
```

`─<` تعني "واحد إلى كثير".

## Bounded Contexts (لمحة)

في MVP 0 الـ Domain صغير، فنبدأ بـ **Bounded Context واحد** اسمه "الإدارة المالية الشخصية"، مع فصل واضح لـ **الهوية** (التسجيل وكلمات المرور) كجزء تقني منفصل.

لما يدخل Open Banking في MVP 1، غالبًا يصير له Context خاص ("استيراد العمليات") يترجم بيانات البنك إلى Transaction حقنا. هذي فائدة إن الـ Domain ما يعرف شيء عن Lean.
