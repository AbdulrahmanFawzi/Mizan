# ميزان — Domain Discovery
## الخطوة 2: Business Rules (نطاق MVP 0)

**Business Rule:** حقيقة أو قيد في عالم المشكلة، يبقى صحيحًا مهما كانت التقنية (ويب، جوال، Oracle، أي شيء).
كل قاعدة هنا لازم يصير لها Unit Test لاحقًا.

الرموز:
- **[قرار]** = حسمته أنت (في الخطوة 1 أو بعد مراجعة الخطوة 2)
- **[مقترح]** = اقترحته أنا، راجعه وغيّره إذا ما يناسبك
- بدون رمز = قاعدة واضحة من الـ PRD أو من طبيعة المشكلة

---

## 1. المال (Money)

| ID | القاعدة |
|---|---|
| BR-M1 | كل المبالغ بالريال السعودي (SAR) في MVP 0، لكن العملة تُخزَّن مع كل مبلغ |
| BR-M2 | المبالغ بدقة هللتين (منزلتين عشريتين)، ولا تُستخدم أنواع الكسور العائمة (float/double) |
| BR-M3 | ما يُجمع أو يُطرح مبلغين بعملتين مختلفتين |

## 2. المستخدم والهوية

| ID | القاعدة |
|---|---|
| BR-U1 | البريد الإلكتروني فريد — ما يتكرر بين حسابين |
| BR-U2 | المستخدم يشوف ويعدّل بياناته فقط. أي محاولة للوصول لبيانات غيره تُرفض |
| BR-U3 | حذف الحساب يحذف كل بياناته المالية |

## 3. الدخل

| ID | القاعدة |
|---|---|
| BR-I1 | الدخل الشهري أكبر من صفر |
| BR-I2 | **[مقترح]** تعديل الدخل ما يغيّر حدود الفئات تلقائيًا، لكن يعيد حساب "غير المخصص" |

## 4. فترة الميزانية

| ID | القاعدة |
|---|---|
| BR-P1 | **[قرار D1]** كل مستخدم يحدد يوم بداية فترته (من 1 إلى 31) |
| BR-P2 | **[مقترح]** إذا اليوم المختار غير موجود في الشهر (مثل 31 في أبريل، أو 30 في فبراير)، تبدأ الفترة آخر يوم في ذلك الشهر |
| BR-P3 | الفترة تبدأ في يوم البداية وتنتهي في اليوم اللي قبل بداية الفترة التالية. مثال: يوم 27 ← الفترة من 27 أكتوبر إلى 26 نوفمبر |
| BR-P4 | **[قرار]** تغيير يوم البداية يطبَّق من الفترة القادمة، والفترة الحالية تبقى كما هي |
| BR-P5 | لكل مستخدم ميزانية واحدة فقط لكل فترة |
| BR-P6 | **[قرار D2]** عند بداية فترة جديدة تُنسخ الفئات والحدود من الفترة السابقة، والمصروف يبدأ من صفر |
| BR-P7 | المصروف ينتمي للفترة اللي يقع فيها **تاريخ المصروف**، مو تاريخ إدخاله |
| BR-P8 | **[مقترح]** بعد تغيير يوم البداية، الفترة الانتقالية تبدأ بعد نهاية الحالية وتنتهي قبل أقرب يوم بداية جديد. إذا طلعت أقصر من 15 يوم، تمتد للي بعده. مثال: الحالية تنتهي 26 نوفمبر واليوم الجديد 1 ← 27 نوفمبر إلى 30 نوفمبر (4 أيام) قصيرة، فتصير 27 نوفمبر إلى 31 ديسمبر |

## 5. فئات الميزانية

| ID | القاعدة |
|---|---|
| BR-B1 | اسم الفئة فريد داخل الميزانية الواحدة |
| BR-B2 | الحد الشهري للفئة صفر أو أكثر. إذا كان صفر، أي صرف عليها يُعتبر تجاوز |
| BR-B3 | **[قرار D3 + D4]** فئتين نظاميتين موجودتين دائمًا ولا تُحذفان: **"أخرى"** و **"الادخار"** |
| BR-B4 | **[قرار]** حذف فئة عليها مصروفات ينقل مصروفاتها إلى "أخرى" |
| BR-B5 | **[قرار]** مجموع حدود الفئات مسموح يتجاوز الدخل، لكن النظام يعرض تحذير "تخصيص زائد" |
| BR-B6 | **المصروف** = مجموع مصروفات الفئة في الفترة |
| BR-B7 | **المتبقي** = الحد − المصروف (ممكن يكون سالب = تجاوز) |
| BR-B8 | **نسبة الاستهلاك** = المصروف ÷ الحد × 100 |
| BR-B9 | **غير المخصص** = الدخل − مجموع حدود الفئات |
| BR-B10 | كل فئة موجودة عند المستخدم لها حد واحد بالضبط في كل ميزانية. إضافة فئة جديدة تضيف لها حد في ميزانية الفترة الحالية |

## 6. المصروفات (Transactions)

| ID | القاعدة |
|---|---|
| BR-T1 | المبلغ أكبر من صفر |
| BR-T2 | **[قرار D3]** الفئة إلزامية، والفئة لازم تكون من ميزانية نفس المستخدم |
| BR-T3 | التاريخ إلزامي، و **[مقترح]** ما يكون في المستقبل |
| BR-T4 | **[مقترح]** اسم التاجر اختياري |
| BR-T5 | تعديل أو حذف مصروف يعيد حساب الفئة المتأثرة (وإذا تغيّرت الفئة أو الفترة، يعيد حساب القديمة والجديدة) |

## 7. التنبيهات

| ID | القاعدة |
|---|---|
| BR-A1 | عتبات التنبيه: 80% و 90% و 100% من حد الفئة |
| BR-A2 | كل عتبة تُرسَل **مرة واحدة فقط** لكل فئة في كل فترة |
| BR-A3 | إذا مصروف واحد تخطّى أكثر من عتبة (مثلًا من 70% إلى 105%)، يُرسَل تنبيه **أعلى عتبة فقط** |
| BR-A4 | ما فيه تنبيهات تجاوز على فئة **"الادخار"** — تجاوز الادخار شيء إيجابي |
| BR-A5 | التنبيهات تخص الفترة الحالية فقط. تعديل مصروف في فترة سابقة ما يولّد تنبيه |

## 8. الأهداف المالية

| ID | القاعدة |
|---|---|
| BR-G1 | المبلغ المستهدف أكبر من صفر، والمبلغ الحالي صفر أو أكثر |
| BR-G2 | التاريخ المستهدف لازم يكون في المستقبل عند الإنشاء |
| BR-G3 | **المتبقي** = المستهدف − الحالي |
| BR-G4 | **الادخار الشهري المطلوب** = المتبقي ÷ عدد الفترات المتبقية حتى التاريخ المستهدف (حد أدنى فترة واحدة) |
| BR-G5 | **[مقترح]** الادخار الشهري المطلوب **يُقرَّب للأعلى** لأقرب ريال (6,500 ÷ 12 = 541.67 ← **542**، مو 541 مثل الـ PRD) |
| BR-G6 | مبلغ الإضافة للهدف أكبر من صفر |
| BR-G7 | **[قرار D4]** الإضافة للهدف تزيد المبلغ الحالي للهدف **وتُحسب مصروفًا من فئة "الادخار"** في الفترة اللي يقع فيها تاريخها |
| BR-G8 | إذا وصل الحالي للمستهدف أو تجاوزه، حالة الهدف تصير **"مكتمل"** |
| BR-G9 | إذا مرّ التاريخ المستهدف بدون اكتمال، حالة الهدف تصير **"متأخر"**، والمستخدم يقدر يمدد التاريخ |

## 9. الذكاء المالي (Insights)

| ID | القاعدة |
|---|---|
| BR-N1 | **نسبة الانحراف** = (الفعلي − المخطط) ÷ المخطط × 100. مثال: 1,270 مقابل 1,000 = **27% أكثر** |
| BR-N2 | **معدل الصرف اليومي** = مصروف الفئة ÷ الأيام المنقضية من الفترة (شاملة اليوم) |
| BR-N3 | **المتوقع نهاية الفترة** = المعدل اليومي × عدد أيام الفترة |
| BR-N4 | إذا المتوقع أكبر من الحد، يظهر Insight "متوقع تتجاوز" |
| BR-N5 | **[قرار]** التوقع ما يظهر قبل مرور 3 أيام من الفترة، لأن البيانات قليلة والتوقع يطلع مبالغ فيه |
| BR-N6 | الـ Insights استشارية فقط. النظام ما يحوّل أموال ولا ياخذ قرار عن المستخدم |
